# Security Rules

## Общие принципы

- безопасность учитывается на уровне frontend, Supabase и базы данных;
- frontend не считается доверенной средой;
- данные, пришедшие от пользователя, нельзя считать безопасными;
- критические проверки должны выполняться на серверной стороне или на уровне Supabase;
- секретные ключи не должны попадать во frontend-код;
- не хранить service role key в Angular-приложении.

---

## Валидация данных

- все пользовательские данные должны проходить валидацию;
- обязательные поля должны проверяться;
- длина строк должна иметь ограничения;
- числовые значения должны проверяться на допустимый диапазон;
- значения из select/radio/enum должны проверяться на допустимые варианты;
- frontend-валидация используется для удобства пользователя, но не считается достаточной защитой;
- критические проверки должны дублироваться на стороне Supabase/backend.

---

## Supabase

- использовать только `anon` key во frontend;
- `service_role` key запрещено использовать в Angular-приложении;
- доступ к данным должен контролироваться через Supabase Row Level Security (RLS);
- RLS должен быть включён для таблиц, содержащих пользовательские или чувствительные данные;
- политики RLS должны ограничивать чтение, создание, изменение и удаление данных;
- нельзя полагаться только на проверки в Angular-компонентах для защиты данных;
- прямой доступ к таблицам из frontend допустим только при наличии соответствующих RLS-политик.

---

## Аутентификация

- использовать Supabase Auth;
- состояние авторизации не должно определяться только на основании данных из frontend;
- защищённые маршруты должны использовать Angular guards;
- права доступа должны дополнительно контролироваться на стороне Supabase через RLS;
- logout должен корректно завершать пользовательскую сессию;
- не хранить пароль пользователя самостоятельно.

---

## Авторизация

- проверять права доступа перед выполнением защищённых операций;
- frontend UI не является механизмом защиты;
- скрытие кнопки или страницы не считается защитой;
- окончательное разрешение на чтение или изменение данных определяется политиками Supabase/RLS;
- административные операции должны быть доступны только соответствующим пользователям.

---

## Формы

- все пользовательские формы должны иметь валидацию;
- нельзя доверять данным только потому, что они прошли Angular-валидацию;
- значения должны проверяться перед отправкой в Supabase;
- текстовые поля должны иметь разумные ограничения по длине;
- ошибки валидации должны показываться пользователю без раскрытия внутренней информации системы.

---

## File Uploads

Для загрузки файлов:

- ограничивать допустимые типы файлов;
- проверять MIME type;
- проверять расширение файла;
- ограничивать размер файла;
- использовать безопасные имена файлов;
- не использовать пользовательское имя файла как единственный идентификатор;
- хранить файлы в Supabase Storage;
- использовать Storage policies для ограничения доступа;
- не предоставлять публичный доступ к файлам без необходимости;
- не загружать и не обрабатывать исполняемые файлы без явной необходимости;
- не считать проверку расширения достаточной для безопасности файла.

---

## XSS

- не использовать `innerHTML` без необходимости;
- избегать `bypassSecurityTrust...` без обоснованной необходимости;
- не вставлять непроверенный пользовательский HTML;
- не отключать встроенную защиту Angular без необходимости;
- пользовательский текст должен выводиться обычными Angular bindings.

---

## API и внешние данные

- не доверять данным, полученным из внешних API;
- проверять данные перед использованием в приложении;
- не помещать секретные API keys во frontend;
- внешние запросы должны использовать HTTPS;
- ошибки внешних сервисов не должны раскрывать секретные данные пользователю.

---

## Ошибки

- пользователю не показывать stack trace;
- не показывать внутренние SQL/database errors;
- не раскрывать API keys, tokens и другие секреты;
- пользовательские сообщения об ошибках должны быть понятными и безопасными;
- технические ошибки должны логироваться отдельно от пользовательского сообщения.

---

## Логи

Не записывать в логи:

- пароли;
- access tokens;
- refresh tokens;
- service role keys;
- другие секреты;
- чувствительные персональные данные без необходимости.

Логи должны содержать только информацию, необходимую для диагностики проблемы.

---

## Secrets

Запрещено хранить в репозитории:

- Supabase service role key;
- пароли;
- приватные API keys;
- access tokens;
- refresh tokens;
- другие секретные credentials.

Публичный Supabase `anon` key может находиться во frontend-конфигурации, но безопасность данных должна обеспечиваться RLS, а не сокрытием этого ключа.

---

## Dependencies

- использовать актуальные версии зависимостей в пределах совместимости проекта;
- не добавлять библиотеку без необходимости;
- проверять новые зависимости перед добавлением в проект;
- удалять неиспользуемые зависимости;
- при обнаружении критической уязвимости зависимости рассмотреть обновление или замену пакета.

---

## Security Changes

Изменения, затрагивающие:

- authentication;
- authorization;
- RLS;
- Supabase Storage policies;
- пользовательские данные;
- загрузку файлов;
- секреты;
- доступ к административным функциям;

должны быть отдельно проверены перед завершением задачи.

---

## Основное правило

Frontend нельзя считать доверенной средой.

Любая критическая проверка безопасности должна выполняться на стороне, которой доверяется принятие решения: Supabase/RLS или backend/Edge Function.

Angular отвечает за UX и клиентскую валидацию, но не является границей безопасности.
