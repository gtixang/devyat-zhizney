# Code Style

## Общие правила

- писать простой и читаемый код;
- не создавать абстракции заранее;
- не создавать универсальные решения без реальной необходимости;
- не писать слишком большие функции и методы;
- одна основная ответственность на файл/класс/функцию;
- предпочитать ранний `return` вместо глубокой вложенности;
- давать понятные имена переменным, функциям, классам и компонентам;
- избегать ненужных сокращений;
- придерживаться единого стиля во всём проекте;
- не дублировать существующую логику без необходимости.

---

## Технические правила

Подробные правила для конкретных технологий описаны в отдельных документах:

- `docs/specs/styles.md` — SCSS и стили;
- `docs/specs/ts.md` — TypeScript;
- `docs/specs/angular-html.md` — Angular templates, HTML, ARIA, доступность и семантическая разметка.

## TypeScript

- использовать `strict` mode;
- не использовать `any` без обоснованной необходимости;
- предпочитать точные типы вместо `any`;
- использовать `interface` и `type` по назначению;
- использовать `readonly`, если значение не должно изменяться;
- предпочитать небольшие функции с одной ответственностью;
- избегать глубокой вложенности;
- использовать ранний `return`, когда это делает код понятнее;
- не использовать классы без необходимости;
- не создавать абстрактные базовые классы только ради переиспользования нескольких строк кода.

---

## Angular

- использовать standalone components;
- не использовать NgModules для новой функциональности;
- использовать Angular Signals для локального состояния UI;
- использовать RxJS для асинхронных потоков и операций, где он действительно необходим;
- использовать `ChangeDetectionStrategy.OnPush`;
- использовать `inject()` вместо constructor injection, если это соответствует стилю проекта;
- не помещать бизнес-логику непосредственно в шаблоны;
- не обращаться к Supabase напрямую из компонентов;
- не создавать сложные компоненты с чрезмерным количеством ответственности;
- использовать lazy loading для крупных страниц и разделов.

---

## Angular Components

Каждый компонент должен иметь понятную ответственность.

## Данные, константы и типы

### Mock-данные

- Mock-данные не должны храниться внутри Angular-компонентов.
- Mock-данные необходимо выносить в отдельные файлы.
- Mock-данные должны находиться рядом с функциональностью, которой они принадлежат.
- Не создавать глобальную директорию для mock-данных всего приложения.
- Если mock-данные относятся ко всему business context, хранить их в соответствующем context.
- Если mock-данные нужны только конкретной feature, хранить их рядом с этой feature.

### Константы

- Значимые и переиспользуемые константы не должны объявляться внутри компонента.
- Константы необходимо выносить в отдельные файлы.
- Константы должны находиться как можно ближе к функциональности, которой они принадлежат.
- Не создавать глобальную директорию `constants/` без реальной необходимости.
- Локальные значения, используемые только внутри конкретного компонента и не имеющие самостоятельного смысла, можно оставлять в компоненте.

### Типы

- Не объявлять domain-модели и переиспользуемые типы непосредственно внутри Angular-компонентов.
- Типы должны находиться рядом с функциональностью, которой они принадлежат.
- Типы предметной области размещать в `domain` соответствующего business context.
- Типы, относящиеся только к конкретной feature или UI-компоненту, можно размещать рядом с этой feature.
- Не создавать глобальную директорию `types/` для всех типов приложения без реальной необходимости.
- Не дублировать один и тот же тип в разных файлах.
- Перед созданием нового типа необходимо проверить, существует ли уже подходящий тип в соответствующем context.
